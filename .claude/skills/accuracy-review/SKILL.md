# accuracy-review

`accuracy-cycle` Skillの出力（diff・仮説・ベースライン比較表）を受け取り、**コミットしていい変更かどうか**を判定する。通常のコードレビュー（バグ・簡潔さ）に加えて、このプロジェクト特有の「結果の正しさ」を見るのが目的。

## チェック項目

### A. コードレビュー（一流のレビュアーが実際に考えていること）

「動くことを確認する」のではなく「どう壊れるか」を能動的に探す。以下はチェックリストではなく、読みながら自問する観点。

1. **この直し方で正しいか（設計の理解）**
   - バグ/要望に対して、ここを直すのが根本か。症状だけ消す対症療法になっていないか
   - 例: ルールの閾値だけ変えて逃げていないか。ラグ欠損の扱いなど特徴量側の根本原因を見ているか

2. **壊し方を探す（adversarial read）**
   - 「動く入力」ではなく「一番嫌な入力」を考える: 候補検知が0件、API が 429/5xx、WebSocket が切れたまま復帰しない、DB に想定外の欠損がある
   - この変更が例外的な市場状況（ボラ急増、出来高ゼロ、連続同値）でどう振る舞うか

3. **境界・異常系**
   - if の境界（以上/未満の取り違え）、null・空配列、タイムアウト、リトライの上限
   - 例: `AiClient` の3秒タイムアウト後に本当にルールのみへフォールバックしているか。NaN のラグ値が後続の計算に伝播して黒く壊れないか

4. **不変条件が崩れていないか**
   - 「システムが常に満たすべきこと」をこの変更が黒く破っていないか
   - 例: 同じ足のシグナルが2回保存されない、通知のクールダウンが再起動後も効く、`candles` に欠損が残らない

5. **本番での影響範囲（Blast Radius）と気づけるか**
   - 間違っていた場合、どこまで被害が広がるか。静かに壊れて誰も気づかない経路がないか
   - 例: 誤った BUY 判定が実際の通知に繋がる。障害通知の仕組み自体が壊れていて、障害に気づけなくなっていないか
   - 「これが本番で3時に壊れたら、ログ/通知から原因を追えるか」を自問する

6. **テストの質（量ではない）**
   - テストが実装をなぞっただけ（タウトロジー）になっていないか。このテストは、直したバグ/防ぎたい退行を実際に検出できるか
   - 例: ウォークフォワードの「未来のデータを使っていない」ことを、たまたま通るのではなく明示的に検証できているか

7. **差分の最小性・可読性**
   - 仮説1つに対して変更が最小か。関係ない整形・リファクタが混ざって本質が見えにくくなっていないか
   - 名前が「実装の都合」でなく「意図」を表しているか。半年後の自分が読めるか

8. **外部入力・秘匿情報への不信**
   - 外から来るもの（Binance応答、AIサービスの出力）を信用せず検証しているか
   - 秘密情報（Webhook URL等）をログに出していないか（既存の `DiscordNotifier` の方針を壊していないか）

9. **テストが通っているか**
   - `pytest` / `gradlew test` が通っていなければ、上記を検討する前に即NG

### B. 統計的な妥当性（ここが本命）

1. **未来の情報を使っていないか（リーク）**
   - 特徴量やラベル作成で、予測時点より後の情報を使っていないか
   - `walk_forward.py` は各区間で「その区間より前のデータだけ」で学習し直す設計。候補の変更がこの前提を壊していないか（例: 全期間で1回だけ学習したモデルを使い回していないか）

2. **多重比較・たまたまの良化でないか**
   - `accuracy-cycle` の手順どおり、ベースラインと**同一条件**（期間・オプション）で比較しているか。期間や閾値を変えて都合の良い結果を選んでいないか
   - `winning_folds`（5区間中何区間プラスか）を見る。合計がプラスでも1区間の大勝ちに頼っている場合はNG、または「限定的な改善」として明記させる
   - 試した組み合わせの数に対して改善幅が小さい場合は、偶然である可能性を指摘する

3. **ベースラインとの比較で退行していないか**
   - PF・最大DD・合計損益・勝率のどれかが明確に悪化していて、他の指標の改善で正当化できていなければNG
   - 「勝率は上がったがPFが下がった」のようなトレードオフがある場合、何を優先するかの説明があるか

4. **再現性**
   - 比較に使ったコマンド（`--to` 等のオプション）が両方（ベースライン・候補）で記録されていて、再現できるか

## 指摘の書き方

A/Bで気になった点を書くときは、**断定せず、対話を促す言い方＋根拠**にする。レビュアーが常に正しいとは限らないし、断定だと書いた人が身構えて会話が終わる。

状況に応じて次のパターンを使い分ける（確認形・提案形の2つに限らない）。

- **確認形**（意図が読み取れない・仕様通りか自信がないとき）
  - 型: 「〜という理解で合っていますか？」
  - 例: 「`AiClient` がタイムアウトした場合はルール一致のみで BUY 扱いにする、という理解で合っていますか？（`AiException` の catch 節がそう読めたので確認したいです）」
- **提案形**（動作に問題はないが改善案があるとき）
  - 型: 「〜のほうがわかりやすいかもしれません」
  - 例: 「`threshold` という変数名より `probabilityThreshold` のほうが、他の閾値と混同せずわかりやすいかもしれません」
- **事実形**（断定していいこと＝再現・実行して確認できることに限る）
  - 型: 「`[ファイル:行]` 〜。`[背景・再現条件]`」
  - 例: 「`core-java/.../RuleEngine.java:42` `rsi_low` の比較が `<=` のままで、境界値 35.00 のときに想定と逆の判定になります。既存テストはちょうど境界をまたがないケースしか見ていません」
  - ここは確認形にせず、事実をそのまま言い切る方が親切（相手に事実確認の手間を取らせない）
- **判断を仰ぐ形**（トレードオフがあり、レビュー側だけでは決めきれないとき）
  - 型: 「〜について、A（...）と B（...）のどちらを優先しますか？」
  - 例: 「利確幅を1.2%にすると勝率は+3pt上がりますがPFは1.18→1.05に下がります。勝率とPF、どちらを優先する方針ですか？」
- **検出有無の明示形**（「見たが問題なかった」と「見ていない」を混同させないため）
  - Bの各チェック項目には、見つからなかった場合も含めて必ず結果を書く: 「リーク: なし」「多重比較: なし（ベースラインと同一条件で実行）」「退行: 最大DDのみ -1pt、他は改善のため許容」
  - 何か見つかった場合は「〜: あり（n件）」として件数を明示する

**どのパターンでも根拠を1行添える**。根拠のない指摘（「なんとなく気になる」）は書かない。根拠の例: 具体的なファイル/行、再現する入力例、既存コードとの矛盾、ベースラインの数値。

### 指摘しなくていいこと（ノイズを減らす）

- `CLAUDE.md` の規約通りの書き方（例: コミット分割の仕方、README更新の有無）を、規約を知らないていで指摘しない
- フォーマッタ/lintの領分（インデント・空行など）
- 実害のない好みの差で、すでに🟢任意として出した内容を角度を変えて何度も言う

### レビューが見逃したことが後で分かったら

本番やあとのレビューで「このチェックで防げたはずの問題」が見つかった場合、個別の指摘として終わらせず、**このSKILL.md自身のA/Bチェック項目に1行追記する**（次回から自動的に見るようにする）。レビューの精度を上げるのもループの対象。

### 優先度をつける

指摘が複数あるときは、どれを先に直すべきか分かるように**必ず優先度をつけて、優先度の高い順に並べる**。

| 優先度 | 基準 | 例 |
| --- | --- | --- |
| 🔴 必須 | コミット前に直さないと合格にできない。不変条件違反・リーク・既存機能の破壊・テスト失敗・秘密情報の漏出・ベースラインからの退行で説明がない | 「同じ足でシグナルが2回保存されませんか？（根拠: ...）」 |
| 🟡 推奨 | 今回は見逃せるが、早めに直した方がいい。将来のバグの元になる書き方、説明が欲しいトレードオフ、カバーされていない異常系 | 「タイムアウト時のフォールバックのテストがなさそうですが、追加した方がよいかもしれません（根拠: ...）」 |
| 🟢 任意 | 動作・安全性に影響しない。可読性・命名・好みの範囲 | 「`threshold` より `probabilityThreshold` のほうがわかりやすいかもしれません（根拠: ...）」 |

🔴 が1つでもあれば判定は「不合格」または「要修正」になる（🔴を残したまま「合格」にはしない）。🟡・🟢 だけなら「合格」にしつつ、次のアクションに申し送りしてよい。

## 判定の出し方

以下の形式で結論を出す。

```
## 判定: 合格 / 不合格 / 要修正

### 気になった点（優先度の高い順）
- 🔴 必須（事実形）: `[ファイル:行]` 〜。背景: ...
- 🔴 必須（確認形）: 〜という理解で合っていますか？（根拠: ...）
- 🟡 推奨（判断を仰ぐ形）: 〜について A と B、どちらを優先しますか？（根拠: ...）
- 🟢 任意（提案形）: 〜のほうがわかりやすいかもしれません（根拠: ...）
  ※ 優先度は🔴→🟡→🟢の順に並べる。パターンは確認形/提案形/事実形/判断を仰ぐ形から状況に合うものを選ぶ

### 検出有無（Bのチェック項目は該当なしでも明記）
- リーク: なし / あり（n件）
- 多重比較・たまたまの良化: なし（ベースラインと同一条件） / あり
- ベースラインからの退行: なし / あり（項目名・数値、許容する理由があれば書く）

### 判定の根拠
- （A/Bのチェック項目全体を見て、合格/不合格/要修正に至った理由を具体的な数値つきで）

### 次のアクション
- 合格: コミットしてよい（コミット文に残す数値を指定）
- 不合格: revertして、次に試すべき仮説の方向性（分かれば）
- 要修正: 直すべき箇所と、直した後に再実行すべき手順
```

「気になった点」が全部確認・提案止まりでも、判定自体（合格/不合格/要修正）は明確に出す。指摘の言い方を柔らかくすることと、ゲートとしての結論を曖昧にすることは別。

**「要修正」は再度 `accuracy-cycle` のステップ4〜6に戻す。** 「合格」判定が出るまでコミットしない。
